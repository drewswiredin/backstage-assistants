backstage-assistants — config flow

One declarative assistants: block in app-config.yaml defines multiple assistant profiles — each with its own prompt, access policy, tools, allowed models, and a few UI options. This maps how that config is validated, split into secret / backend-only vs browser-safe, exposed via /status, and applied on the frontend.

The config surface (one block, many profiles)

assistants:
  # ---------- global ----------
  defaultModel: openai:gpt-5.5          # required
  maxSteps: 8
  registerCoreActions: true
  providers:
    openai:
      apiKey: ${OPENAI_API_KEY}        # 🔒 @visibility secret — backend only
      baseUrl: https://api.openai.com/v1
      models: [gpt-5.5, gpt-4o-mini]
  ui:                          # global UI defaults — deep-merged into every profile
    composer: { placeholder: "Send a message…" }
    suggestions: []

  # ---------- profiles (multiple assistants) ----------
  profiles:
    general:
      title: General Assistant
      description: Catalog + TechDocs helper.
      prompt: |                     # 🔒 backend only — never sent to browser
        You are a Backstage developer-portal assistant…
      access: { allowAuthenticated: true }   # 🔒 backend only
      actions: [search-catalog, search-techdocs, read-techdocs]
      ui:                       # per-profile overrides (win over global ui)
        suggestions:
          - { title: "Who owns…", prompt: "Who owns the payments service?" }

    docs:
      title: Docs Assistant
      prompt: | …
      access: { groups: [group:default/platform] }  # 🔒
      actions: [search-techdocs, read-techdocs]
      models: [openai:gpt-4o-mini]     # optional allowlist (subset of pool; omit = full pool)
      defaultModel: openai:gpt-4o-mini   # required when the allowlist excludes the global default

No theme key — see "Theme" below.

Exposure — secret/backend-only vs browser-safe

The browser only receives the browser rows (via /status) and only sends back { assistantId, modelId, messages }. Prompt, keys, and access never leave the backend.

UI options (v1) & theme

Resolved per profile via deepMerge(global ui, profile.ui), returned in /status, applied to the chat. Objects deep-merge; arrays (e.g. suggestions) replace so a profile can clear inherited values.

ui keyEffect
suggestions[]starter prompt chips on the empty thread
composer.placeholdercomposer input placeholder text
welcome heading/subtextderived automatically from the profile's title/description

Theme: a single built-in palette that follows Backstage's light/dark mode automatically — not configurable. Deferred: file attachments (needs an upload path + multimodal model) and fine-grained toggles (branch picker, action-bar buttons) — the merge pipeline already supports them; they light up later with no config change.

Settled decisions

  1. Block shape: assistants.profiles.{id} — global settings + a named map of assistant profiles.
  2. UI options (v1): suggestions[] + composer.placeholder; welcome text derived from title/description. Attachments & extra toggles deferred.
  3. Theme: one built-in palette, auto-synced to Backstage light/dark. Not configurable — keeps it simple and always-consistent with the host.
  4. Models: global pool + optional per-profile models allowlist (subset of pool; omit = all) + per-profile defaultModel. A profile's effective default must be within its allowlist; a restricted profile that excludes the global default must declare its own.
  5. Merge semantics: ui objects deep-merge; arrays replace.
