backstage-assistants — config flow

The assistants: block defines platform, secrets, and safety — providers, MCP server connections, runtime guards, and the global approval floor. Assistant definitions — title, prompt, access, tools, models, per-assistant UI — live in the plugin's own database and are created and edited at runtime through the in-plugin admin editor. This traces the config↔DB seam: how config is validated and split into secret / backend-only vs browser-safe, how definitions are stored and snapshotted, and how the two merge at /status and /chat. Sister doc: architecture.

1Flow

Two sources meet at the runtime. Config carries platform, secrets, and the safety floor; the database carries the editable assistant definitions (including each assistant's composer placeholder + suggestions), rebuilt into an in-memory snapshot on every write. Both are split by visibility, and only the browser-safe half ever reaches the client — prompts, API keys, MCP credentials, and access rules stay server-side.

2Config surface

Platform, secrets, and safety only — no assistant profiles. Per-assistant definitions are created in the admin editor, not here. Secrets marked *. 

# app-config.yaml
assistants:
  # ---- global ----
  defaultModel: openai:gpt-5.5          # required — resolves a null per-assistant default
  maxSteps: 10                          # max tool-call steps per turn (default 10)
  toolResultMaxChars: 30000             # cap one tool result; head+tail truncate (default 30000, 0 = off)
  requestBodyLimit: 10mb                # Express body limit for /chat (default 10mb)
  builtinActions: true                  # register this plugin's 3 read-only Actions (default false)

  providers:
    openai:
      type: openai                      # openai | anthropic | azure | openai-compatible — selects the @ai-sdk/* factory
      apiKey: ${OPENAI_API_KEY}          # * secret — backend only
      baseUrl: https://api.openai.com/v1
      options: {}                       # passthrough, spread verbatim into the factory
      models:                           # list of objects; ids namespaced as openai:<name>
        - { name: gpt-5.5, contextWindow: 400000, reasoning: true }  # contextWindow drives the gauge; reasoning adds the effort picker
        - { name: my-custom-deployment, maxOutputTokens: 16384 }              # output ceiling, for models the provider misjudges

  # ---- external MCP servers (optional) ----
  mcp:
    connectTimeoutMs: 15000             # global ceiling for connect + listTools (default 8000)
    servers:
      github:                           # remote (Streamable HTTP)
        transport: http
        url: https://mcp.internal/github
        headers:                        # * secret — static per-server credential, NOT run-as-user
          Authorization: ${GITHUB_MCP_TOKEN}
        requireApproval:                # per-server approval floor — these tools always gate, for every assistant
          - delete_repo
      filesystem:                       # local process
        transport: stdio
        command: npx
        args: ["-y", "@modelcontextprotocol/server-filesystem", "/srv/docs"]
        env:                            # * secret
          TOKEN: ${FS_TOKEN}
        connectTimeoutMs: 20000         # per-server override — slow-starting stdio servers (uvx/python ~10s)

  # ---- global approval floor for Backstage actions (a safety floor, not weakenable at runtime) ----
  requireApproval:                      # a listed action always needs Allow/Deny before it runs, for EVERY assistant
    - register-entity
    - unregister-entity

  # NOTE: per-assistant definitions — title · prompt · access · allowedTools · models · defaultModel · ui · color
  # are created and edited in the admin UI and stored in the plugin DB, NOT in this file. No profiles: block,
  # and no global ui: block — the composer placeholder and suggestions are per-assistant settings.

No assistants.profiles key. Assistant definitions are stored in the plugin database and managed through the admin editor (architecture: assistant management); config keeps only platform, secrets, and the safety floor — the parts that carry secrets or must not be weakenable at runtime. No assistants.database key — conversations and assistant definitions both use Backstage's standard backend.database (the same database the catalog and search already require). No theme key — see §4. No global ui key — the composer placeholder and starter suggestions are per-assistant settings edited in the admin editor, not platform config.

3Field exposure

Where each field goes, and whether it crosses to the browser. Config rows split browser vs backend; assistant definitions are served from the DB (full defs via the admin-gated /manage/assistants; browser-safe summaries via /status). The browser sends back { assistantId, modelId, threadId, reasoningLevel?, messages }; the transport also carries its own id, trigger, and messageId.

Field Scope Consumed by
providers.*.apiKey secret provider registry (server)
providers.* (type · baseUrl · options) backend provider registry (server)
mcp.servers.*.headers · env secret MCP transport auth (server)
mcp.servers.* (transport · url · command · args · cwd) backend MCP connection (server)
mcp.connectTimeoutMs · mcp.servers.*.connectTimeoutMs backend ceiling for connect + listTools per server — per-server → global → 8000ms
mcp.servers.*.requireApproval[] backend per-server approval floor — folds into the toolApproval set at /chat (see architecture §4)
requireApproval[] (top-level) backend global action approval floor — folds into the toolApproval set at /chat
maxSteps backend streamText stopWhen (default 10)
toolResultMaxChars backend cap per tool result — head+tail truncate at the tool boundary (default 30000, 0 off)
requestBodyLimit backend Express body-parser limit for /chat (default 10mb)
definition.prompt DB backend instructions at /chat; full def via /manage/assistants — never on /status
definition.access DB backend access gate — /status filter, /chat, and /threads list/status filter + POST /threads
definition.allowedTools[] DB backend unified tool allowlist at /chat — Action ids + namespaced MCP tools (<serverId>__<tool>); derives which MCP servers to connect
definition.title · description DB browser assistant rail / welcome (summary via /status)
definition.color DB browser assistant avatar tint (cosmetic)
definition.models[] · defaultModel DB browser model picker (per-assistant allowlist; empty = full pool) + its default (null = platform default)
providers.*.models[].contextWindow browser per-model max input tokens — composer context-usage gauge
providers.*.models[].reasoning browser flags a reasoning model — shows the per-conversation effort picker; the chosen reasoningLevel rides the /chat body and persists on the thread
providers.*.models[].maxOutputTokens backend output-token ceiling passed to streamText — for models the provider misjudges
definition.ui DB browser composer placeholder + starter suggestions (per-assistant; no global default)
tools (resolved summaries) browser tool list / detail — name · description · source, for both Actions and MCP

Tool summaries are browser-safe; tool execution is not. /status lists each assistant's effective tools (Action + MCP) so the UI can show them; the actual invoke happens only at /chat, under the identities described in the architecture trust model. The MCP tool names come from a background-warmed cache (a scheduled server-side probe), so /status never connects to an MCP server on the request path. Definition reads split too: the public /status serves only browser-safe summaries (titles · models · ui · tool-summaries — never prompt or access), while the full definitions reach the editor via the admin-gated GET /manage/assistants.

4Settled facts

  1. Block shape — assistants: holds platform, secrets, and safety only (global settings · providers · mcp · requireApproval). There is no profiles map; assistant definitions live in the plugin database and are created in the admin editor.
  2. Providers — a type discriminator selects the @ai-sdk/* factory; options is spread verbatim; the union of all models is the pool; a model id is <providerId>:<model>.
  3. MCP — assistants.mcp.servers.{id} defines connections; assistants opt in by listing namespaced tools (<serverId>__<tool>) in allowedTools, and the backend derives which servers to connect from the prefixes present. Each server uses one static credential (headers / env) — a shared identity, not run-as-user.
  4. Approval is global — the safety floor lives in config: top-level requireApproval: [actionId…] plus per-server mcp.servers.*.requireApproval: [tool…]. A listed tool always pauses for Allow/Deny, for every assistant: the backend builds the AI SDK toolApproval map from (floor) ∩ (allowedTools) — enforced in the loop, not weakenable by runtime editing (⚖ badge in the editor), and orthogonal to access: it withholds execution, never grants it. Always-allow grants and batch collapse are UI behaviours, no config — architecture §4 has the full mechanics.
  5. Client-side tools need no config — render_form (inline RJSF forms; renders any scaffolder field extension the host app has registered) and download_file (a download chip for generated artifacts) are always available to the model and resolve in the browser; there is no config key for either (architecture §4).
  6. Models — each provider's models is a list of objects [{ name, contextWindow?, maxOutputTokens?, reasoning? }]: reasoning: true marks a model as reasoning-capable, which surfaces a per-conversation effort picker (the level persists on the thread and is translated to each provider's native knob server-side); maxOutputTokens caps output for models the provider misjudges; the union is the pool. A per-assistant models allowlist (in the DB; empty = full pool) and a nullable defaultModel (null = platform default) are resolved at snapshot-build time: effective models = allowlist or pool, effective default = stored ?? platform default. contextWindow rides through to models[].contextWindow (browser-safe) to drive the composer's context-usage gauge; omit it to leave a model's limit unknown.
  7. Assistants live in the DB + admin editor — definitions are rows in an assistants table (id = immutable server-generated UUID, editable title column for sorting, definition_json blob, audit columns who/when). The blob holds title · description? · color? · prompt · access · allowedTools[] · models[] · defaultModel · ui?. New assistants are created open (allowAuthenticated: true); the create route persists the submitted access as-is. A seed-once marker inserts one all-users default — read-only catalog/TechDocs tools (tolerated if builtinActions is off), on the platform-default model — on first init and never resurrects it once deleted or edited. No redeploy to add an assistant or tweak a prompt.
  8. AssistantStore + snapshot — a Knex store over coreServices.database (mirrors ThreadService) does CRUD and rebuilds an in-memory snapshot write-through on every write; the hot path (router iteration, assistants.get) reads the snapshot synchronously. A lazy ~60s refresh is insurance under the single-replica assumption (one backend replica, or session affinity for /api/assistants/*). The snapshot is where derived-at-read lives, and it tolerates on read — unknown tools/models are skipped rather than fatal.
  9. Permissions — two Backstage permissions defined in -common gate the plugin: assistant.use (the user-facing routes /status · /chat · /threads and the chat surface) and assistant.manage (/manage/* · /capabilities and the editor gear). Registered with coreServices.permissionsRegistry so permission UIs discover them, authorized server-side, and gated client-side with usePermission; the host's permission policy decides who holds them. Which assistants an assistant.use holder sees is the separate per-assistant access policy.
  10. /capabilities feeds the editor live — the admin-gated GET /api/assistants/capabilities returns the live assignable inventory for the editor pickers: actions (from actions.list), the model pool, and MCP servers with their tools and per-server reachability (from the pooled tool cache, 5-min TTL — unreachable is surfaced, not silently empty), plus the global approval floor so the editor can badge gated tools. The action list is scoped to the admin's visibility, so "assignable" can be a superset of "runnable by every user" (tolerated at runtime).
  11. Delta-validation, never blocks save — pickers offer only live items (no free typing). New additions are validated against live capabilities (client and server); pre-existing assignments are grandfathered; removals are always allowed; strict structural validation (InputError on bad shape); users/groups are lenient (a dangling group simply grants nobody). Stale assignments are highlighted — RED = definitively gone (model not in pool / action not in registry / MCP server removed / tool absent from a reachable server), AMBER = unverifiable (tool whose MCP server is currently unreachable). Save never auto-strips stale entries (a transient outage must not delete a good assignment); the admin prunes on demand.
  12. The config↔DB seam — secrets and the safety floor stay in config (providers, MCP credentials, runtime guards, the approval floor) because they carry secrets or must not be weakenable at runtime; assistant content and assignment (title · prompt · access · allowedTools · models · ui · color) live in the editable DB. The two merge at the snapshot/runtime: config provides the pool and the floor; the DB provides the definition that selects from them.
  13. UI is per-assistant — the composer placeholder and starter suggestions live on each assistant's definition (ui), edited in the admin editor; there is no global platform default. The welcome subtitle is the assistant's description (a generic default when absent); the greeting is personalized from the signed-in profile.
  14. Theme — one built-in palette that follows Backstage light/dark automatically. Not configurable, by design.
  15. Persistence — conversations and assistant definitions are both stored server-side via Backstage's backend.database; no new config key (see architecture §6).
  16. Access is the boundary — every conversation is scoped to its owner (user_ref) AND filtered to currently-accessible assistants: /threads + /threads/status only return conversations for assistants the caller can access, and POST /threads is gated — so removing an assistant (or revoking access) removes its conversations and its unread. Threads that reference a deleted assistant orphan and are filtered out on read; recreate the assistant via the admin UI.
  17. Runtime guards — global, backend-only: maxSteps (tool-call steps/turn, default 10), toolResultMaxChars (cap one tool result, head+tail truncate, default 30000, 0 disables), requestBodyLimit (Express body limit, default 10mb).
