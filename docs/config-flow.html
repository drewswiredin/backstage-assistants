backstage-assistants — config flow

The assistants: block defines platform, secrets, and safety — providers, MCP server connections, runtime guards, the admin allowlist, and the global approval floor. Assistant definitions — title, prompt, access, tools, models, per-assistant UI — live in the plugin's own database and are created and edited at runtime through the in-plugin admin editor. This traces the config↔DB seam: how config is validated and split into secret / backend-only vs browser-safe, how definitions are stored and snapshotted, and how the two merge at /status and /chat. Sister doc: architecture.

1Flow

Two sources meet at the runtime. Config carries platform, secrets, and the safety floor; the database carries the editable assistant definitions, rebuilt into an in-memory snapshot on every write. Both are split by visibility, and only the browser-safe half ever reaches the client — prompts, API keys, MCP credentials, and access rules stay server-side.

2Config surface

Platform, secrets, and safety only — no assistant profiles. Per-assistant definitions are created in the admin editor, not here. Secrets marked *.

# app-config.yaml
assistants:
  # ---- global ----
  defaultModel: openai:gpt-5.5          # required — resolves a null per-assistant default
  maxSteps: 10                          # max tool-call steps per turn (default 10)
  toolResultMaxChars: 30000             # cap one tool result; head+tail truncate (default 30000, 0 = off)
  requestBodyLimit: 10mb                # Express body limit for /chat + /title (default 10mb)
  builtinActions: true                  # register this plugin's 3 read-only Actions (default false)

  providers:
    openai:
      type: openai                      # selects the @ai-sdk/* factory
      apiKey: ${OPENAI_API_KEY}          # * secret — backend only
      baseUrl: https://api.openai.com/v1
      options: {}                       # passthrough, spread verbatim into the factory
      models:                           # list of objects; ids namespaced as openai:<name>
        - { name: gpt-5.5, contextWindow: 400000 }   # contextWindow drives the composer gauge
        - { name: gpt-4o-mini }                      # omit contextWindow = gauge shows count without a limit

  # ---- external MCP servers (optional) ----
  mcp:
    servers:
      github:                           # remote (Streamable HTTP)
        transport: http
        url: https://mcp.internal/github
        headers:                        # * secret — static per-server credential, NOT run-as-user
          Authorization: ${GITHUB_MCP_TOKEN}
        requireApproval:                # per-server approval floor — these tools always gate, for every assistant
          - delete_repo
      filesystem:                       # local process
        transport: stdio
        command: npx
        args: ["-y", "@modelcontextprotocol/server-filesystem", "/srv/docs"]
        env:                            # * secret
          TOKEN: ${FS_TOKEN}

  ui:                                   # global UI defaults — the platform default, deep-merged UNDER each assistant's ui
    composer: { placeholder: "Send a message…" }
    suggestions: []

  # ---- who may manage assistants (default-deny if unset/empty) ----
  admins:
    users: [user:default/jdoe]
    groups: [group:default/platform-admins]

  # ---- global approval floor for Backstage actions (a safety floor, not weakenable at runtime) ----
  requireApproval:                      # a listed action always needs Allow/Deny before it runs, for EVERY assistant
    - register-entity
    - unregister-entity

  # NOTE: per-assistant definitions — title · prompt · access · allowedTools · models · defaultModel · ui · color
  # are created and edited in the admin UI and stored in the plugin DB, NOT in this file. No profiles: block.

No assistants.profiles key. Assistant definitions are stored in the plugin database and managed through the admin editor (architecture: assistant management); config keeps only platform, secrets, and the safety floor — the parts that carry secrets or must not be weakenable at runtime. No assistants.database key — conversations and assistant definitions both use Backstage's standard backend.database (the same database the catalog and search already require). No theme key — see §4.

3Field exposure

Where each field goes, and whether it crosses to the browser. Config rows split browser vs backend; assistant definitions are served from the DB (full defs via the admin-gated /manage/assistants; browser-safe summaries via /status). The browser sends back only { assistantId, modelId, threadId, messages }.

Tool summaries are browser-safe; tool execution is not. /status lists each assistant's effective tools (Action + MCP) so the UI can show them; the actual invoke happens only at /chat, under the identities described in the architecture trust model. Definition reads split too: the public /status serves only browser-safe summaries (titles · models · ui · tool-summaries — never prompt or access), while the full definitions reach the editor via the admin-gated GET /manage/assistants.

4Settled facts

  1. Block shape — assistants: holds platform, secrets, and safety only (global settings · providers · mcp · ui · admins · requireApproval). There is no profiles map; assistant definitions live in the plugin database and are created in the admin editor.
  2. Providers — a type discriminator selects the @ai-sdk/* factory; options is spread verbatim; the union of all models is the pool; a model id is <providerId>:<model>.
  3. MCP — assistants.mcp.servers.{id} defines connections; assistants opt in by listing namespaced tools (<serverId>__<tool>) in allowedTools, and the backend derives which servers to connect from the prefixes present. Each server uses one static credential (headers / env) — a shared identity, not run-as-user.
  4. Approval is global — the safety floor lives in config: top-level requireApproval: [actionId…] for Backstage actions plus per-server mcp.servers.*.requireApproval: [tool…]. A listed tool always pauses for an Allow/Deny before it runs, for every assistant. The backend sets the AI SDK needsApproval predicate to (global approval set) ∩ (the assistant's allowedTools) — deterministic, enforced in the loop, not prompt-driven, and not weakenable by runtime assistant-editing. The editor shows a read-only 🔒 badge on globally-gated tools. Orthogonal to access/authorization — it withholds execution, it does not grant it. The chat adds an Always allow action (a standing per-tool grant for the rest of the conversation, read back from history) and collapses parallel same-tool prompts into one counter card — both UI behaviours, no extra config (architecture §4).
  5. Interactive forms need no config — the render_form tool is always available to the model (a client-side tool resolved in the browser); there is no config key for it. It renders any scaffolder field extension the host app has registered (architecture §4).
  6. Models — each provider's models is a list of objects [{ name, contextWindow? }] (the old parallel contextWindows map is gone); the union is the pool. A per-assistant models allowlist (in the DB; empty = full pool) and a nullable defaultModel (null = platform default) are resolved at snapshot-build time: effective models = allowlist or pool, effective default = stored ?? platform default. contextWindow rides through to models[].contextWindow (browser-safe) to drive the composer's context-usage gauge; omit it to leave a model's limit unknown.
  7. Assistants live in the DB + admin editor — definitions are rows in an assistants table (id = immutable server-generated UUID, editable title column for sorting, definition_json blob, audit columns who/when). The blob holds title · description? · color? · prompt · access · allowedTools[] · models[] · defaultModel · ui?. New assistants default to access-deny (so a draft isn't exposed before review); a seed-once marker inserts one all-users default — read-only catalog/TechDocs tools (tolerated if builtinActions is off), on the platform-default model — on first init and never resurrects it once deleted or edited. No redeploy to add an assistant or tweak a prompt.
  8. AssistantStore + snapshot — a Knex store over coreServices.database (mirrors ThreadService) does CRUD and rebuilds an in-memory snapshot write-through on every write; the hot path (router iteration, assistants.get) reads the snapshot synchronously. A lazy ~60s refresh is insurance under the single-replica assumption. The snapshot is where derived-at-read lives, and it tolerates on read — unknown tools/models are skipped rather than fatal.
  9. Admin allowlist + canManage — assistants.admins (users/groups) is evaluated server-side with the same ownership-ref check used for assistant access, default-deny, and independent of permission.enabled (so disabling permissions can't silently open management to everyone). /status returns canManage to gate the gear; the /manage/* and /capabilities endpoints independently 403 non-admins. Admin membership lives in config precisely because it can't live in the editable DB (privilege escalation).
  10. /capabilities feeds the editor live — the admin-gated GET /api/assistants/capabilities returns the live assignable inventory for the editor pickers: actions (from actions.list), the model pool, and MCP servers with their tools and per-server reachability (from the cached listServerToolsRaw, 5-min TTL — unreachable is surfaced, not silently empty). A manual refresh busts the cache. The action list is scoped to the admin's visibility, so "assignable" can be a superset of "runnable by every user" (tolerated at runtime).
  11. Delta-validation, never blocks save — pickers offer only live items (no free typing). New additions are validated against live capabilities (client and server); pre-existing assignments are grandfathered; removals are always allowed; structural (zod) validation is strict; users/groups are lenient (a dangling group simply grants nobody). Stale assignments are highlighted — RED = definitively gone (model not in pool / action not in registry / MCP server removed / tool absent from a reachable server), AMBER = unverifiable (tool whose MCP server is currently unreachable). Save never auto-strips stale entries (a transient outage must not delete a good assignment); the admin prunes on demand.
  12. The config↔DB seam — secrets and the safety floor stay in config (providers, MCP credentials, runtime guards, the admin allowlist, the approval floor) because they carry secrets or must not be weakenable at runtime; assistant content and assignment (title · prompt · access · allowedTools · models · ui · color) live in the editable DB. The two merge at the snapshot/runtime: config provides the pool, the floor, and the platform UI default; the DB provides the definition that selects from them.
  13. UI merge — deepMerge(global ui, assistant.ui): objects deep-merge, arrays replace (so an assistant can clear inherited values). The global ui is the platform default, merged under each assistant's own. Welcome text is derived from title / description.
  14. Theme — one built-in palette that follows Backstage light/dark automatically. Not configurable, by design.
  15. Persistence — conversations and assistant definitions are both stored server-side via Backstage's backend.database; no new config key (see architecture §6).
  16. Access is the boundary — every conversation is scoped to its owner (user_ref) AND filtered to currently-accessible agents: /threads + /threads/status only return chats for agents the caller can access, and POST /threads is gated — so removing an agent (or revoking access) removes its conversations and its unread. Threads that reference a deleted assistant orphan and are filtered out on read; recreate the assistant via the admin UI.
  17. Runtime guards — global, backend-only: maxSteps (tool-call steps/turn, default 10), toolResultMaxChars (cap one tool result, head+tail truncate, default 30000, 0 disables), requestBodyLimit (Express body limit, default 10mb).
