backstage-assistants — config flow

One declarative assistants: block defines global settings, providers, MCP servers, and many assistant profiles. This traces how that config is validated, split into secret / backend-only vs browser-safe, exposed via /status, and applied at /chat. Sister doc: architecture.

1Flow

Config is parsed once on the backend, split by visibility, and only the browser-safe half ever reaches the client. Secrets — prompts, API keys, MCP credentials, access rules — stay server-side.

2Config surface

One block, many profiles. Secrets marked *.

# app-config.yaml
assistants:
  # ---- global ----
  defaultModel: openai:gpt-5.5          # required
  maxSteps: 10                          # max tool-call steps per turn (default 10)
  toolResultMaxChars: 30000             # cap one tool result; head+tail truncate (default 30000, 0 = off)
  requestBodyLimit: 10mb                # Express body limit for /chat + /title (default 10mb)
  registerCoreActions: true             # register this plugin's built-in Actions (default false)

  providers:
    openai:
      type: openai                      # selects the @ai-sdk/* factory
      apiKey: ${OPENAI_API_KEY}          # * secret — backend only
      baseUrl: https://api.openai.com/v1
      options: {}                       # passthrough, spread verbatim into the factory
      models: [gpt-5.5, gpt-4o-mini]    # model ids namespaced as openai:<model>
      contextWindows:                   # optional per-model max input tokens — drives the composer gauge
        gpt-5.5: 400000                 # omit a model = gauge shows the count without a limit

  # ---- external MCP servers (optional) ----
  mcp:
    servers:
      github:                           # remote (Streamable HTTP)
        transport: http
        url: https://mcp.internal/github
        headers:                        # * secret — static per-server credential, NOT run-as-user
          Authorization: ${GITHUB_MCP_TOKEN}
      filesystem:                       # local process
        transport: stdio
        command: npx
        args: ["-y", "@modelcontextprotocol/server-filesystem", "/srv/docs"]
        env:                            # * secret
          TOKEN: ${FS_TOKEN}

  ui:                                   # global UI defaults — deep-merged into every profile
    composer: { placeholder: "Send a message…" }
    suggestions: []

  # ---- profiles (one per assistant) ----
  profiles:
    general:
      title: General Assistant
      description: Catalog + TechDocs helper.
      color: "#0b6b6b"                  # optional avatar tint — browser-safe, cosmetic
      prompt: |                         # * secret — system prompt, never sent to browser
        You are a Backstage developer-portal assistant…
      access: { allowAuthenticated: true }   # * secret — who may use this assistant
      actions: [search-catalog, search-techdocs, read-techdocs]  # run as the user
      mcpServers:                       # opt in to MCP servers + optional per-tool allowlist
        - { server: github, tools: ["search_issues", "get_file"] }
        - { server: filesystem }        # omit tools = all tools from that server
      ui:
        suggestions:
          - { title: "Who owns…", prompt: "Who owns the payments service?" }

    docs:
      title: Docs Assistant
      prompt: |
        …
      access: { groups: [group:default/platform] }     # *
      actions: [search-techdocs, read-techdocs]
      models: [openai:gpt-4o-mini]      # optional allowlist (subset of pool; omit = full pool)
      defaultModel: openai:gpt-4o-mini  # required when the allowlist excludes the global default

No assistants.database key. Conversation persistence uses Backstage's standard backend.database — the same database the catalog and search already require. No operator action beyond having one configured. No theme key — see §4.

Tool summaries are browser-safe; tool execution is not. /status lists each assistant's effective tools (Action + MCP) so the UI can show them; the actual invoke happens only at /chat, under the identities described in the architecture trust model.

4Settled facts

  1. Block shape — assistants.profiles.{id}: global settings + a named map of profiles, one per assistant.
  2. Providers — a type discriminator selects the @ai-sdk/* factory; options is spread verbatim; the union of all models is the pool; a model id is <providerId>:<model>.
  3. MCP — assistants.mcp.servers.{id} defines connections; profiles opt in via mcpServers: [{ server, tools? }]. Each server uses one static credential (headers / env) — a shared identity, not run-as-user.
  4. Models — global pool + optional per-profile models allowlist (subset of pool; omit = all) + per-profile defaultModel. A profile's effective default must lie within its allowlist. Optional per-provider contextWindows: { <model>: tokens } rides through to models[].contextWindow (browser-safe) to drive the composer's context-usage gauge; omit a model to leave its limit unknown.
  5. UI merge — deepMerge(global ui, profile.ui): objects deep-merge, arrays replace (so a profile can clear inherited values). Welcome text is derived from title / description.
  6. Theme — one built-in palette that follows Backstage light/dark automatically. Not configurable, by design.
  7. Persistence — conversations are stored server-side via Backstage's backend.database; no new config key (see architecture §5).
  8. Access is the boundary — every conversation is scoped to its owner (user_ref) AND filtered to currently-accessible agents: /threads + /threads/status only return chats for agents the caller can access, and POST /threads is gated — so removing an agent (or revoking access) removes its conversations and its unread.
  9. Runtime guards — global, backend-only: maxSteps (tool-call steps/turn, default 10), toolResultMaxChars (cap one tool result, head+tail truncate, default 30000, 0 disables), requestBodyLimit (Express body limit, default 10mb).
