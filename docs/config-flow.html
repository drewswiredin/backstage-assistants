backstage-assistants — config flow DRAFT — for review

One declarative assistants: block in app-config.yaml defines multiple assistants — each with its own prompt, access, tools, and UI options. This maps how that config is validated, split into secret / backend-only vs browser-safe, exposed via /status, and applied on the frontend (including the shadcn / assistant-ui UI knobs).

The config surface (one block, many assistants)

assistants:
  # ---------- global ----------
  defaultModel: openai:gpt-5.5
  maxSteps: 8
  registerCoreActions: true
  providers:
    openai:
      apiKey: ${OPENAI_API_KEY}      # 🔒 @visibility secret — backend only
      baseUrl: https://api.openai.com/v1
      models: [gpt-5.5, gpt-4o-mini]
  ui:                          # global UI defaults — deep-merged into every assistant
    theme: default            # shadcn token set / data-aui-theme
    composer:
      allowAttachments: false
      placeholder: "Send a message…"
    suggestions: []
    branchPicker: true

  # ---------- multiple assistant definitions ----------
  definitions:
    general:
      title: General Assistant
      description: Catalog + TechDocs helper.
      prompt: |                     # 🔒 backend only — never sent to browser
        You are a Backstage developer-portal assistant…
      access: { allowAuthenticated: true }   # 🔒 backend only
      actions: [search-catalog, search-techdocs, read-techdocs]
      ui:                       # per-assistant overrides (win over global ui)
        composer: { allowAttachments: true }
        suggestions:
          - { title: "Who owns…", prompt: "Who owns the payments service?" }

    docs:
      title: Docs Assistant
      prompt: | …
      access: { groups: [group:default/platform] }  # 🔒
      actions: [search-techdocs, read-techdocs]
      ui: { theme: mono }

Where each field goes

Exposure — secret/backend-only vs browser-safe

FieldScopeConsumed by
providers.*.apiKeysecretprovider registry (server)
promptbackendsystem at /chat
accessbackendaccess gate (/status filter + /chat)
actions[]backendtool allowlist at /chat
maxStepsbackendstreamText stopWhen
title, descriptionbrowserassistant rail / welcome
models, defaultModelbrowsermodel picker
ui (resolved)browserThread/composer knobs

The browser only ever receives the browser rows (via /status) and only sends back { agentId, modelId, messages }. Prompt, keys, and access never leave the backend.

UI knobs & the deep-merge

Resolved per assistant: deepMerge(global ui, definition.ui) → returned in /status → applied to the assistant-ui Thread.

ui keyEffect on the chat
composer.allowAttachmentsshow the + attach button / dropzone
suggestions[]starter prompt chips on the empty thread
composer.placeholdercomposer input placeholder text
branchPickershow/hide message branch navigation
themeshadcn token set (data-aui-theme) + radius
actionBar (copy/reload/edit)which per-message actions render

v1 builds the full merge pipeline (global → per-assistant → /status → applied) but wires a subset of knobs; the rest expand later without changing the plumbing.
