# Actions consumed in-process, run as the user

The `/chat` loop turns Backstage Actions into the model's tools by consuming the Actions registry **in-process** — `actions.list({ credentials })` then `actions.invoke({ id, input, credentials })` — using the **caller's** credentials throughout, never a service/static token. MCP (`*-mcp-backend`) is not on this path; it is only an exposure for external clients. The plugin registers its own read-only core actions in-process via `actionsRegistryServiceRef` (gated by `registerCoreActions`), because a vanilla Backstage registry is otherwise empty of catalog/TechDocs/search actions.

Authorization is two independent gates: the Assistant's `actions[]` **allowlist** (explicit names or wildcard; omitting it grants no tools) and **Backstage's own permission checks**. The effective toolset for a request is `allowlist ∩ actions the caller can see`. Coarse permission filtering is free at `list` (denied `visibilityPermission` is dropped); fine-grained, resource-level permission is enforced at `invoke` because the handler runs as the user — it cannot be pre-computed, since it depends on the runtime input (which entity, who owns it). A denied or failed invoke is caught and returned as a structured tool result the model can explain, not thrown — the turn continues.

We chose this over the POC's MCP-bridge-with-a-static-service-token because that gave global tools with no per-user enforcement. In-process + caller credentials removes the network hop and the shared-identity escalation: a user can never reach data through a tool that they couldn't reach directly. This is the plugin's core security model, so it is recorded here.
