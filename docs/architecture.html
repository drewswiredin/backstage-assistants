backstage-assistants — architecture

The intended design. An in-portal AI chat for Backstage, built by stitching assistant-ui (chat UI), the Vercel AI SDK (model + tool loop), and Backstage (auth, Actions, database) with thin glue. This is the blueprint we build to — see PRINCIPLES.md.

2Components & wiring

Two packages we own (teal) talking to external systems across a trust boundary (dashed). One runtime carries every conversation across all agents — switching agent or conversation never remounts it, so in-flight streams keep running. The frontend holds no conversation state of its own; it is a view of the server. Assistant definitions live in the database (an in-memory snapshot, §8); config carries only platform, secrets, and the safety floor.

One tool set, two identities. The loop receives Backstage Actions and MCP tools as a single tool list, but they execute under different credentials — see §5. A tool may also pause for the user before running — see §4.

Config ↔ DB seam. readConfig() carries only platform, secrets, and the safety floor — providers (apiKey), MCP connections (headers / env), runtime guards, and the global requireApproval floor — things that hold secrets or must not be weakenable at runtime. Assistant definitions (name · color · prompt · access · allowedTools · models · per-assistant UI) live in the assistants table and are read from the AssistantStore snapshot by the access gate and tool assembly. The admin editor edits the store; config never holds assistant content (§8).

3Chat turn

A single /chat request. The server is the only writer of message rows: it persists the user's message at the START of the turn and the completed turn on finish — so the conversation is durable the instant it's sent and a reply is never lost if the browser navigates away mid-stream.

Thread lifecycle (separate from a turn). On mount the runtime loads the list (GET /threads — every conversation across all agents, filtered to ones the caller can access) and the active thread's messages (GET /threads/:id/messages); selecting a thread marks it read (POST /threads/:id/read). Create / rename / archive / delete are REST calls through the RemoteThreadListAdapter. New conversations are created only via "+" (typing never forks) — a bare agent with no conversation shows an empty state; deleting the active conversation lands on the agent's most-recent remaining chat, else that empty state. The browser keeps no conversation state of its own.

Oversized tool results are capped. A tool result longer than toolResultMaxChars (default 30000) is truncated head+tail with an elision marker at the tool boundary — on both the success and error paths — so one huge result can't overflow the context window or bloat the stored turn; the model is told it was truncated and can refine. Failures surface — no silent endings. When a turn errors, the backend formats the real reason into the streamed error part (not a masked default) and the UI shows it; and a stream that ends without finishing — a disconnect, or a provider stream that dies server-side and escapes the SDK's error path — is surfaced too (see Stop & end-states below). A turn never just stops with no reason.

Stop & end-states. The composer Stop posts POST /chat/cancel/:threadId, which aborts this turn's server-side AbortController (ownership-checked against the in-flight set). A bare disconnect does not abort — that means "navigate away / reload" and the turn keeps running for resume. The surface labels every non-normal ending from the AI SDK's finish signal so none is silent: an aborted/stopped turn → neutral "Request interrupted" (the partial reply is persisted and stamped metadata.canceled, so it shows live — a client store keyed by message id — and durably on any client); a dropped or cut-off stream → "Connection lost"; a clean failure → the streamed error part above. A legitimate human-in-the-loop pause (a form or a pending approval) is never mistaken for a cut-off.

Token usage rides the turn. The final step's input+output tokens are attached to the assistant message (AI SDK messageMetadata) and recorded per thread; GET /threads/status returns the last turn's total as tokens, which the composer renders as a context-usage gauge against the model's configured contextWindow (§7). assistant-ui's transport drops live message metadata, so the server is the source of truth here.

Reasoning effort rides the conversation. A model flagged reasoning: true in config surfaces an Effort picker (default / low / medium / high / xhigh) next to the model picker; the chosen reasoningLevel travels in the /chat body, persists on the thread (reasoning_level, PATCHed on change), and is translated server-side into each provider's native option (OpenAI reasoning effort; Anthropic adaptive thinking) — config owns every provider-specific knob. Switching to a non-reasoning model clears the picker.

Attachments. The composer accepts pasted or picked files (one adapter for images and documents alike, 7 MB cap; rejections surface as alerts). Sent attachments persist with the message and render as chips; before the model call, non-image file parts are inlined as <attachment name="…"> text so any model can read them, while images pass through natively. A second inline pass normalises tool-call arguments for Anthropic models.

Auto-title. The first completed turn also titles the conversation: /chat's onFinish fires a small off-path generateText when the thread is still "New Chat", persists the result, and emits an updated signal (the standalone POST /title route exists but the client no longer calls it).

A turn may pause for the user. The loop above is the autonomous path. A tool call can instead render an interactive form or wait for explicit approval before running — both resolve back into this same turn. See §4.

Interactive forms — render_form. A client-side tool: declared with a schema but no server execute, so streamText emits the call and yields to the browser. The surface renders it inline (makeAssistantToolUI) through scaffolder's own RJSF <Form>, fed the live field-extension registry from formFieldsApiRef.loadFormFields() — so any built-in or app-registered scaffolder picker (OwnerPicker, EntityPicker, RepoUrlPicker, …) renders by name, with no per-field code here. ui:* keys embedded in the schema (the scaffolder-template convention) are hoisted into the uiSchema via scaffolder's extractSchemaFromStep, so a template's parameter block works verbatim. The user's submit becomes the tool result via addResult and the turn auto-resumes; cancelling — or ignoring the form and sending a new message — resolves it as dismissed, never as a value. Use it whenever structured / multi-field / multiple-choice input beats a bulleted question in chat. download_file is a second always-available client-side tool (also schema-only, no server execute): the model calls it to hand a generated artifact back as a download chip in chat, resolved entirely in the browser — neither is config-gated.

Deterministic approval gate — global requireApproval. A safety floor in config, not a per-assistant setting: the top-level requireApproval (Backstage action ids) plus each MCP server's requireApproval (tool names) name the tools that must be confirmed before they run, for every assistant. The backend sets the AI SDK's needsApproval predicate to the intersection of that global floor and the assistant's allowedTools; the SDK then emits a tool-approval-request and skips the tool's execute until the user answers. The surface shows an Allow / Always allow / Deny card with the exact tool input (respondToApproval, bridged to the SDK's addToolApprovalResponse by useAISDKRuntime); Allow runs the action server-side under its normal identity, Deny returns an execution-denied result to the model. The gate is enforced in the loop — not a prompt the model can route around — and is orthogonal to authorization (§5): a human checkpoint, while Backstage's per-user permissions still apply when an approved Action invokes. Because the floor lives in config, runtime assistant-editing can never weaken it — the editor marks a globally-gated tool with an approval (⚖) badge. Names not in any assistant's tool set are simply never reached.

Batch ergonomics. Two affordances keep a long agentic run from becoming a wall of clicks, both deterministic. Always allow records a standing grant — an approval response tagged always:<tool>; the needsApproval predicate reads it back from the conversation history (persisted, so it survives reloads) and skips the prompt for that tool for the rest of the chat — per-tool, so granting one never auto-approves another. And when the agent fires several gated calls of the same tool in one step (parallel), the surface collapses them into one card with a count; the lowest-index pending call leads and the rest mirror its decision, so a single Allow / Always allow / Deny resolves the whole batch.

Both resume the same turn. The form result and the approval response are written onto the latest assistant step; the composer's sendAutomaticallyWhen flushes once that step is fully settled (every tool part submitted or approved/denied) and at least one is a client-driven resolution — so a server tool truncated at maxSteps is never auto-resumed. The model then continues with the new tool results in context.

5Identity & authorization

The trust model. Tools reach the model from two sources with two different identities — this is the single most important property to get right. A separate axis, admin management, decides who may edit assistant definitions at all.

Unified allowedTools. One string[] per assistant. Each entry is either a bare Backstage action id (e.g. search-catalog) or a namespaced MCP tool (<serverId>__<toolName>); the backend derives which MCP servers to connect from the prefixes present. Entries are explicit only — there is no serverId__* wildcard in v1, so a future tool added to a server is never auto-granted. This is exactly the merged namespace the loop already builds its tool list from (§2).
Deny by default. An empty allowedTools yields no tools at all. The access policy gates whether a user may use the assistant at all (resolved server-side against userEntityRef / ownershipEntityRefs).
Consequence. A low-privilege user chatting with an assistant wired to a powerful MCP server gets that server's full configured access — Backstage's per-user permissions do not apply on the MCP path. Choose MCP servers and the scope of their credentials deliberately.
Approval is a separate axis. The global requireApproval floor (§4) adds an orthogonal human checkpoint before a tool runs — it never grants access, it withholds execution pending an explicit Allow. It is config-only and applies to every assistant.

Permissions. Two Backstage permissions gate the plugin: assistant.use (load the surface and converse) on every user-facing route, and assistant.manage (run the admin editor) on /manage/* + /capabilities and the header gear. Both are defined in -common, authorized server-side, and gated client-side with usePermission; the host's permission policy decides who holds them (the backend README shows a policy example). A user without assistant.use is denied if they reach the page directly; hiding the nav entry is the host app's job (the plugin exports the nav icon and the demo app's sidebar wraps it in a usePermission gate — document this in the host when adopting). Which assistants an assistant.use holder sees is the separate per-assistant access policy.

Adapters (the only glue). RemoteThreadListAdapter backs the thread list (list / create / rename / archive / delete / title) over /threads; ThreadHistoryAdapter loads a thread's messages over /threads/:id/messages. Message writes are not a client concern — the server persists the user message at turn start and the full turn on finish (§3). useRemoteThreadListRuntime provides the switcher, active-thread state, and (de)serialization for free. The history adapter is passed directly into useAISDKRuntime rather than published via context — context only survives when the consumer's tree resolves a single @assistant-ui/core, and a nested duplicate would silently reopen every thread blank.
Unread is server-computed (updated_at vs last_read_at) and surfaced through thread metadata — no client-side unread store.
Metadata edits don't touch updated_at. Rename / model / pin / archive update only their own fields; updated_at moves solely when a turn lands (replaceMessages). So it tracks activity + recency, not edits — editing a conversation never falsely marks it unread or reorders the list.

AssistantStore — snapshot + write-through. The assistants table is fronted by an AssistantStore (mirrors ThreadService: Knex over coreServices.database) that keeps an in-memory snapshot rebuilt on every write (write-through). The single-replica assumption makes write-through instant; a lazy ~60 s safety refresh is insurance. /status and the access filter read the snapshot synchronously; /chat and /title deliberately do an authoritative store read instead, so a turn never runs against a stale definition. Snapshot build is where derived-at-read lives: hasModelAllowlist = models non-empty; effective models = the allowlist or the full pool; effective defaultModel = stored value ?? the platform default (never a hardcoded provider:model).
Seed-once. First init inserts one neutral default assistant plus a marker, and never resurrects it — a deleted or edited default stays that way. The default is allowAuthenticated: true (the deliberate all-users exception), defaultModel: null (resolves to the platform default at read), and allowedTools = the three built-in read-only actions (search-catalog / search-techdocs / read-techdocs, tolerated if builtinActions is off).
Tolerate-on-read drift. Reads skip unknown tools and models rather than failing, and threads that reference a deleted/unknown assistant id orphan and are filtered out — recreate the assistant via the admin UI (§8).

7Notifications & live streaming

Parallel background conversations across assistants. Every indicator is a pure derivation of one server snapshot (GET /threads/status); Signals just invalidate it. An in-memory, thread-keyed resumable stream lets you rejoin a generation you stepped away from.

One derived source, no client state machine. Every dot is computed from the single GET /threads/status snapshot (per conversation: working + unread). Rollups: an assistant shows working if any of its conversations is, else unread (working wins); the nav icon rolls the same up across all agents. working shows even for the conversation you're viewing; unread is suppressed for it (focusing marks it read). One StatusDot renders every indicator (amber = working, red = unread).
Signals invalidate; they don't drive state. The backend emits the four signals on the per-user assistants:threads channel; the client simply refetches the snapshot (debounced) — plus on tab-visible, never on window focus, so indicators stay live while the tab is backgrounded. working is the backend's in-flight set; unread is server-authoritative in the DB (updated_at vs last_read_at). Access-filtered: the snapshot only includes agents the caller can access — remove an agent or revoke access and its conversations and unread vanish.
Live resume, keyed by thread. Each /chat turn buffers its SSE under the thread id. On entering a thread the client checks the server working flag and, if a turn is in flight, rejoins via GET /chat/resume/:threadId — replaying buffered + live chunks — with no fragile per-turn id to capture. Because the user message is persisted at turn start, re-entry always shows the conversation even mid-flight. The buffer is held for ~60 s after the turn completes, then dropped — a later re-entry simply loads the durable turn from the DB. In-memory buffer ⇒ single backend replica; the completed turn is durable in the DB regardless.
Context-usage gauge. The same GET /threads/status snapshot carries each conversation's last-turn tokens (final-step input+output, recorded server-side). The composer's 2-level layout renders a circular gauge — used / the model's contextWindow (from /status, configured per model; absent ⇒ no limit shown) — tinted the assistant color. Switching a conversation to a model whose window is smaller than its history shows a "Context exceeded" warning (the model picker is never filtered).

8Assistant management

Assistants are created and edited at runtime — no redeploy to add one or tweak a prompt. The admin editor reads the live capability inventory, only ever offers items that actually exist, and writes back to the AssistantStore, whose snapshot rebuild immediately surfaces the change in /status and the next /chat. Config keeps only platform / secrets / safety; the database holds every definition.

Source of truth = DB-only. Assistants are created in the editor. Config under assistants: carries platform / secrets / safety only: defaultModel, maxSteps, toolResultMaxChars, requestBodyLimit (runtime guards); builtinActions (registers this plugin's three built-in read-only actions, default false); providers.{id} (type / apiKey / baseUrl / options, with models: [{ name, contextWindow?, maxOutputTokens?, reasoning? }]); mcp.servers.{id} (connection plus a per-server requireApproval: [toolName…]); and the top-level requireApproval: [actionId…] floor (§4). Everything else — name · color · description · prompt · access · allowedTools · models · per-assistant ui — is a DB definition. There is no profiles config block.

Capabilities — the live assignable inventory. GET /api/assistants/capabilities (admin-gated) feeds the editor pickers: actions from actions.list(credentials) (scoped to the admin's visibility — assistants run as the requesting user, so "assignable" can be a superset of "runnable by every user", tolerated at runtime), the model pool, and mcpServers from the cached probeServerTools (reachability-aware; same 5-min cache) with per-server reachability surfaced (reachable + error?) rather than silently empty on failure, plus the global approval floor so the editor can badge gated tools.

MCP connections are pooled and maintained server-side — /status never blocks on them. The plugin keeps one persistent client per configured server. A background task (the plugin's coreServices.scheduler) connects what isn't connected, refreshes each server's tools into a warm cache, and reconnects dropped links every few minutes — each connect and listing bounded by that server's connectTimeoutMs (default 8s, per-server → global → built-in), so one black-holed server can't stall the cycle. GET /status reads the cache synchronously — zero MCP connections on the request path — so clicking the plugin is instant regardless of how many MCP servers are configured or whether one is slow (its tools fill in on the next warm cycle). /chat executes through the pooled connection and opens nothing: a server that is momentarily down returns a graceful "not connected" tool result and is healed by the next cycle. This is "tolerate drift" (§8) applied to MCP — serve a warm snapshot, refresh off the hot path.

Delta-validation, never destructive. The pickers offer only live items — no free typing, no ad-hoc names. New additions are validated against live capabilities (client and server); pre-existing assignments are grandfathered and never re-checked; removals are always allowed. Structure uses strict structural validation server-side (InputError on bad shape); users/groups are lenient (a dangling group simply grants nobody). Stale assignments are highlighted: RED = definitively gone (model not in pool / action not in registry / MCP server removed / tool absent from a reachable server); AMBER = unverifiable (a tool whose MCP server is currently unreachable — don't advise pruning something that may be fine). Save is never blocked by stale entries and never auto-strips — a transient outage must not delete a good assignment — so the admin prunes on demand (✕).

Editor surface & controls. A large modal Dialog (90vh, master-detail: assistant list left, edit form right), opened from a gear in the ChatChrome header shown only with the assistant.manage permission. Controls: Prompt multiline; Color hex/picker + a live avatar preview (reuses resolveAssistantColor / AssistantAvatar). Models, Tools, and Access are each a shared AssignList — an assigned-row list plus a searchable "＋ Add" popover. Models from the pool (empty allowlist = all models, the hint then names the platform default) with a ★ default toggle per row (the first model added auto-becomes the default; removing the default promotes the next, so a restricted list always has an in-list default) and an ⓘ showing the full provider:model id + context window. Tools grouped by source — Backstage runs-as-you actions first, then one group per MCP server — over the live /capabilities inventory; each row leads with a run-as icon (👤 the calling user for Backstage actions / 🔑 the server's shared credential for MCP tools), shows a ⚖ approval badge when the tool is in the global floor, and an ⓘ description; stale assignments are flagged RED (gone) / AMBER (unverifiable) with a prune ✕, surfacing the run-as-user (Actions) vs shared-credential / not-run-as-user (MCP) distinction right in the panel (§5). Access shows allowAuthenticated truthfully as an "Any signed-in user" row (no switch); user/group rows come from catalogApiRef, with a typed value accepted as a raw entity ref (freeSolo). Plus a per-assistant UI editor (placeholder + suggestions, deep-merged over the global ui). Save is dirty-tracked (disabled until changed and valid), switching away with unsaved edits prompts "Discard changes?", validation is inline per-field (structural + the new-add-not-live delta rule), and success shows a toast and refreshes the snapshot.

Lifecycle. The id is a server-generated UUID and immutable; the title is editable. A new assistant is created open (allowAuthenticated: true); the editor seeds this and the create route persists the submitted access as-is. A Duplicate action clones to a new id with a "(copy)" title; delete is a hard delete behind a confirm warning that its conversations become inaccessible, and deleting to zero is allowed (an empty state). The assistant list is ordered alphabetically; initial selection is the first assistant.

Write API & the public seam. Under /api/assistants, admin-gated: GET /manage/assistants returns full definitions for the editor, POST / PUT / DELETE /manage/assistants[/:id] mutate, and GET /capabilities serves the inventory above. The public GET /status stays browser-safe — titles / summaries / models / ui / tool-summaries — and never exposes a prompt or the access policy.
