backstage-assistants — architecture

The intended design. An in-portal AI chat for Backstage, built by stitching assistant-ui (chat UI), the Vercel AI SDK (model + tool loop), and Backstage (auth, Actions, database) with thin glue. This is the blueprint we build to — see PRINCIPLES.md.

3Chat turn

A single /chat request. The server is the only writer of message rows: it persists the completed turn on finish, so a reply is never lost if the browser navigates away mid-stream.

sequenceDiagram
  autonumber
  participant U as Browser (assistant-ui)
  participant R as Router
  participant G as Identity / access
  participant A as Tool assembly
  participant L as AI SDK loop
  participant P as LLM provider
  participant T as Action / MCP tool
  participant D as Database

  U->>R: POST /chat { assistantId, modelId, threadId, messages }
  R->>G: resolve user (httpAuth/userInfo) + check access policy
  G-->>R: identity + groups — deny by default
  R->>A: actions.list(credentials) ∩ allowlist + MCP allowlist
  A-->>L: tools — Actions (as user) · MCP (as configured)
  loop reasoning, up to maxSteps
    L->>P: messages + tool schemas
    P-->>L: text or tool call
    alt Backstage Action
      L->>T: invoke as the user
    else MCP tool
      L->>T: call as configured
    end
    T-->>L: result (capped to toolResultMaxChars)
  end
  L-->>U: stream UI messages · errors stream as an error part
  L->>L: consumeStream — finish server-side even if U navigates away
  L->>D: onFinish — persist the completed turn (scoped to user)

Thread lifecycle (separate from a turn). On mount the runtime loads the list (GET /threads) and the active thread's messages (GET /threads/:id/messages); selecting a thread marks it read (POST /threads/:id/read). Create / rename / archive / delete are REST calls through the RemoteThreadListAdapter. The browser keeps no conversation state of its own.

Oversized tool results are capped. A tool result longer than toolResultMaxChars (default 30000) is truncated head+tail with an elision marker at the tool boundary — on both the success and error paths — so one huge result can't overflow the context window or bloat the stored turn; the model is told it was truncated and can refine. Failures surface. When a turn errors (e.g. an over-long prompt), the AI SDK streams the real message as an error part and the UI shows it — not a generic notice.

4Identity & authorization

The trust model. Tools reach the model from two sources with two different identities — this is the single most important property to get right.

Tool sourceRuns asAuthorization gates
Backstage Action
in-process		 as the user
the caller's own Backstage credentials		 (1) the assistant's actions[] allowlist ∩ (2) the user's Backstage permissions, enforced natively at actions.list (visibility) and actions.invoke (per-resource).
External MCP tool
over MCP		 as configured
one static per-server credential (headers / env) — the same identity for every user, not the caller		 (1) the assistant's access policy + (2) its per-profile mcpServers allowlist + (3) an optional per-tool allowlist. No per-user check on this path.

Deny by default. Omitting an Action allowlist yields no Action tools; omitting mcpServers yields no MCP tools. The access policy gates whether a user may use the assistant at all.
Consequence. A low-privilege user chatting with an assistant wired to a powerful MCP server gets that server's full configured access — Backstage's per-user permissions do not apply on the MCP path. Choose MCP servers and the scope of their credentials deliberately.

5Persistence & data model

Conversations live server-side, scoped to their owner. The frontend is a pure view through two assistant-ui adapters; the server is the single source of truth and the only writer of messages.

threads

assistant_idowning assistant (immutable)
user_refowner — every read/write is scoped to it
titlegenerated from the first turn
modellast model id used
pinned · archivedlist state

last_read_atunread = last_read_at ? updated_at > last_read_at : false
messages
idmessage id (primary key)
thread_idparent thread (cascade delete)
parent_idprior message (branching, optional)
roleuser / assistant / system
content_jsonthe assistant-ui message, stored verbatim
sort_orderorder within the thread
created_attimestamp

Adapters (the only glue). RemoteThreadListAdapter backs the thread list (list / create / rename / archive / delete / title) over /threads; ThreadHistoryAdapter loads a thread's messages over /threads/:id/messages. Message writes are not a client concern — the loop persists them on finish (§3). useRemoteThreadListRuntime provides the switcher, active-thread state, and (de)serialization for free.
Unread is server-computed (updated_at vs last_read_at) and surfaced through thread metadata — no client-side unread store.

6Notifications & live streaming

Parallel background conversations across assistants, with real-time indicators pushed over Backstage Signals — and an in-memory resumable stream so you can rejoin a generation you stepped away from.

Status (ConvStatus)IndicatorWhen
read—no activity, already seen (and the one you're viewing)
workingpulsing dota reply is generating and you're not watching this one
unreadred dota reply finished while you weren't looking
Signal · channel assistants:threadsEffect
turn-startedset the conversation working (add to the live set)
turn-finishedclear working; mark unread if not viewing
updatedthread metadata changed (e.g. auto-title) — refresh the list
readthread marked read elsewhere — clear its indicator (cross-view sync)

States are mutually exclusive per conversation and roll up: an assistant shows working if any of its conversations is, else unread — working has authority; the plugin's nav icon shows the same roll-up across all assistants (red dot for unread, subtle pulse while working). The active conversation you're watching is always read — you see the stream itself.
Push, not poll. The backend emits the four signals on the per-user assistants:threads channel via SignalsService; the frontend subscribes with useSignal. The status store is seeded from GET /threads/status on mount and reconciled on window focus. Working is ephemeral live state (an in-memory set on the backend); unread stays server-authoritative in the DB (updated_at vs last_read_at).
Live resume. /chat tees its stream into an in-memory buffer keyed by an x-resumable-stream-id; returning to a still-generating conversation reconnects via GET /chat/resume/:id and replays buffered + live chunks (assistant-ui's AssistantChatTransport resumable option drives the client). In-memory ⇒ single backend replica; a completed turn is always durable in the DB regardless.
