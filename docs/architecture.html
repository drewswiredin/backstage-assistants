backstage-assistants — architecture DRAFT — for review

How the major packages we stitch together — assistant-ui, the Vercel AI SDK, and Backstage — compose into one chat plugin, and how Backstage permissions and the Actions registry become the AI SDK's available tools, executed as the calling user.

Package key

assistant-ui
  • @assistant-ui/react — an open-source library of prebuilt, themeable React components for AI chat.
  • @assistant-ui/react-ai-sdk — connects assistant-ui to the Vercel AI SDK.
Vercel AI SDK
  • ai — the core TypeScript toolkit for building with LLMs: streaming, tool calling, provider-agnostic.
  • @ai-sdk/react — React hooks for AI chat UIs.
  • @ai-sdk/openai · anthropic · azure — adapters for the model providers.
Backstage
  • @backstage/frontend-plugin-api · core-* — Backstage's frontend plugin system.
  • @backstage/backend-plugin-api · backend-openapi-utils — Backstage's backend plugin system, including the Actions registry.
backstage-assistants — this plugin
  • backstage-assistants — this plugin: stitches the packages above into an AI assistants experience for Backstage.

How the key connections work — click to expand

🧰 Backstage Actions → AI SDK tools
  1. Each assistant declares an actions[] allowlist (action names) in app-config.
  2. Per request, actions.list({ credentials }) returns the actions this user may see.
  3. The backend keeps only the assistant's allowlisted names and adapts each to an AI SDK tool() (schema → inputSchema, execute → actions.invoke).
  4. Those tools are handed to the model loop; one source of tools — no parallel tool system (the same registry can also surface over MCP).
🔒 "As the user" — credentials flow through
  1. The request carries the caller's Backstage user token; the backend resolves their identity + groups.
  2. The same credentials are used to both list and invoke actions.
  3. So every tool runs with the caller's own permissions — catalog / TechDocs / search results are scoped to that user, never a service account.
  4. Two independent gates: access policy (may you use this assistant?) and per-tool permissions (what can the tool see, as you?).

Draft. Easy to add on request: the /status + /title routes, the OpenAPI validation layer, local conversation persistence, or the post-MVP external-MCP path.
