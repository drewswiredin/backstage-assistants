backstage-assistants — architecture

The intended design. An in-portal AI chat for Backstage, built by stitching assistant-ui (chat UI), the Vercel AI SDK (model + tool loop), and Backstage (auth, Actions, database) with thin glue. This is the blueprint we build to — see PRINCIPLES.md.

2Components & wiring

Two packages we own (teal) talking to external systems across a trust boundary (dashed). One runtime carries every conversation across all agents — switching agent or conversation never remounts it, so in-flight streams keep running. The frontend holds no conversation state of its own; it is a view of the server.

3Chat turn

A single /chat request. The server is the only writer of message rows: it persists the user's message at the START of the turn and the completed turn on finish — so the conversation is durable the instant it's sent and a reply is never lost if the browser navigates away mid-stream.

Thread lifecycle (separate from a turn). On mount the runtime loads the list (GET /threads — every conversation across all agents, filtered to ones the caller can access) and the active thread's messages (GET /threads/:id/messages); selecting a thread marks it read (POST /threads/:id/read). Create / rename / archive / delete are REST calls through the RemoteThreadListAdapter. New conversations are created only via "+" (typing never forks) — a bare agent with no conversation shows an empty state; deleting the active conversation lands on the agent's most-recent remaining chat, else that empty state. The browser keeps no conversation state of its own.

Oversized tool results are capped. A tool result longer than toolResultMaxChars (default 30000) is truncated head+tail with an elision marker at the tool boundary — on both the success and error paths — so one huge result can't overflow the context window or bloat the stored turn; the model is told it was truncated and can refine. Failures surface. When a turn errors (e.g. an over-long prompt), the AI SDK streams the real message as an error part and the UI shows it — not a generic notice.

Stop cancels the turn. The composer Stop posts POST /chat/cancel/:threadId, which aborts this turn's server-side AbortController (ownership-checked against the in-flight set). A bare disconnect does not abort — that means "navigate away / reload" and the turn keeps running for resume. On abort the partial reply is persisted and stamped metadata.canceled; the UI shows one neutral "Request interrupted" line — live (a client store keyed by message id) and durably on any client (the persisted flag).

Token usage rides the turn. The final step's input+output tokens are attached to the assistant message (AI SDK messageMetadata) and recorded per thread; GET /threads/status returns the last turn's total as tokens, which the composer renders as a context-usage gauge against the model's configured contextWindow (§7). assistant-ui's transport drops live message metadata, so the server is the source of truth here.

A turn may pause for the user. The loop above is the autonomous path. A tool call can instead render an interactive form or wait for explicit approval before running — both resolve back into this same turn. See §4.

4Human-in-the-loop & generative UI

Two ways a tool call pauses for the user instead of running autonomously — both are assistant-ui rendering a tool-call part inline and feeding the answer back into the same turn. Neither depends on the model choosing to ask: the pause is enforced in the loop.

Interactive forms — render_form. A client-side tool: declared with a schema but no server execute, so streamText emits the call and yields to the browser. The surface renders it inline (makeAssistantToolUI) through scaffolder's own RJSF <Form>, fed the live field-extension registry from formFieldsApiRef.loadFormFields() — so any built-in or app-registered scaffolder picker (OwnerPicker, EntityPicker, RepoUrlPicker, …) renders by name, with no per-field code here. ui:* keys embedded in the schema (the scaffolder-template convention) are hoisted into the uiSchema via scaffolder's extractSchemaFromStep, so a template's parameter block works verbatim. The user's submit becomes the tool result via addResult and the turn auto-resumes; cancelling — or ignoring the form and sending a new message — resolves it as dismissed, never as a value. Use it whenever structured / multi-field / multiple-choice input beats a bulleted question in chat.

Deterministic approval gate — requireApproval. A per-profile allowlist of tool names that must be confirmed before they run. For each, the backend sets the AI SDK's needsApproval; the SDK then emits a tool-approval-request and skips the tool's execute until the user answers. The surface shows an Allow / Deny card with the exact tool input (respondToApproval, bridged to the SDK's addToolApprovalResponse by useAISDKRuntime); Allow runs the action server-side under its normal identity, Deny returns an execution-denied result to the model. The gate is enforced in the loop — not a prompt the model can route around — and is orthogonal to authorization (§5): it is a human checkpoint, while Backstage's per-user permissions still apply when an approved Action invokes. Names not in the assistant's tool set are logged and skipped.

Both resume the same turn. The form result and the approval response are written onto the latest assistant step; the composer's sendAutomaticallyWhen flushes once that step is fully settled (every tool part submitted or approved/denied) and at least one is a client-driven resolution — so a server tool truncated at maxSteps is never auto-resumed. The model then continues with the new tool results in context.

5Identity & authorization

The trust model. Tools reach the model from two sources with two different identities — this is the single most important property to get right.

Tool sourceRuns asAuthorization gates
Backstage Action
in-process		 as the user
the caller's own Backstage credentials		 (1) the assistant's actions[] allowlist ∩ (2) the user's Backstage permissions, enforced natively at actions.list (visibility) and actions.invoke (per-resource).
External MCP tool
over MCP		 as configured
one static per-server credential (headers / env) — the same identity for every user, not the caller		 (1) the assistant's access policy + (2) its per-profile mcpServers allowlist + (3) an optional per-tool allowlist. No per-user check on this path.

Deny by default. Omitting an Action allowlist yields no Action tools; omitting mcpServers yields no MCP tools. The access policy gates whether a user may use the assistant at all.
Consequence. A low-privilege user chatting with an assistant wired to a powerful MCP server gets that server's full configured access — Backstage's per-user permissions do not apply on the MCP path. Choose MCP servers and the scope of their credentials deliberately.
Approval is a separate axis. A profile's requireApproval list (§4) adds an orthogonal human checkpoint before a tool runs — it never grants access, it withholds execution pending an explicit Allow. Pair it with the MCP path above when a shared-credential tool warrants a per-call confirmation.

6Persistence & data model

Conversations live server-side, scoped to their owner. The frontend is a pure view through two assistant-ui adapters; the server is the single source of truth and the only writer of messages.

Adapters (the only glue). RemoteThreadListAdapter backs the thread list (list / create / rename / archive / delete / title) over /threads; ThreadHistoryAdapter loads a thread's messages over /threads/:id/messages. Message writes are not a client concern — the server persists the user message at turn start and the full turn on finish (§3). useRemoteThreadListRuntime provides the switcher, active-thread state, and (de)serialization for free.
Unread is server-computed (updated_at vs last_read_at) and surfaced through thread metadata — no client-side unread store.
Metadata edits don't touch updated_at. Rename / model / pin / archive update only their own fields; updated_at moves solely when a turn lands (replaceMessages). So it tracks activity + recency, not edits — editing a conversation never falsely marks it unread or reorders the list.

7Notifications & live streaming

Parallel background conversations across assistants. Every indicator is a pure derivation of one server snapshot (GET /threads/status); Signals just invalidate it. An in-memory, thread-keyed resumable stream lets you rejoin a generation you stepped away from.

Status (ConvStatus)IndicatorWhen

One derived source, no client state machine. Every dot is computed from the single GET /threads/status snapshot (per conversation: working + unread). Rollups: an assistant shows working if any of its conversations is, else unread (working wins); the nav icon rolls the same up across all agents. working shows even for the conversation you're viewing; unread is suppressed for it (focusing marks it read). One StatusDot renders every indicator (amber = working, red = unread).
Signals invalidate; they don't drive state. The backend emits the four signals on the per-user assistants:threads channel; the client simply refetches the snapshot (debounced) — plus on tab-visible, never on window focus, so indicators stay live while the tab is backgrounded. working is the backend's in-flight set; unread is server-authoritative in the DB (updated_at vs last_read_at). Access-filtered: the snapshot only includes agents the caller can access — remove an agent or revoke access and its conversations and unread vanish.
Live resume, keyed by thread. Each /chat turn buffers its SSE under the thread id. On entering a thread the client checks the server working flag and, if a turn is in flight, rejoins via GET /chat/resume/:threadId — replaying buffered + live chunks — with no fragile per-turn id to capture. Because the user message is persisted at turn start, re-entry always shows the conversation even mid-flight. In-memory buffer ⇒ single backend replica; the completed turn is durable in the DB regardless.
Context-usage gauge. The same GET /threads/status snapshot carries each conversation's last-turn tokens (final-step input+output, recorded server-side). The composer's 2-level layout renders a circular gauge — used / the model's contextWindow (from /status, configured per model; absent ⇒ no limit shown) — tinted the assistant color. Switching a conversation to a model whose window is smaller than its history shows a "Context exceeded" warning (the model picker is never filtered).
